> 约束：GitHub Pages 纯静态、零后端零数据库；敏感文件（radio_proxy.py / radio_cookie.json / .env / 音频）永不进 git。

## 四、红线与纪律（自动化也必须遵守）

1. **敏感文件隔离**：watch 脚本只输出结构化数据；radio_proxy.py、radio_cookie.json、.env、secrets.bat、音频永不入 repo（deploy_all 已有敏感文件扫描，auto_update 复用）。
2. **不写死数字**：所有统计由数据计算注入模板。
3. **诚实披露**：演出/取消信息必须人工确认；搜索不到标"待补"，绝不伪造。
4. **幂等提交**：diff 为空则跳过 commit/push/IndexNow，避免垃圾提交。
5. **失败告警**：任何一步异常 → 日志记录 + 不阻塞后续步骤（try/except 隔离），连续失败 3 次在下次运行摘要中提示。
6. **零后端**：一切仍在 GitHub Pages 上静态呈现。

## 五、实施步骤

1. **一次性**：`python project_b/auto_update.py --init` 生成 logs/ 目录、首次基线快照（记录当前各数据文件 hash）。
2. **计划任务**（Windows 任务计划程序）：
   - 名称：`WangXiArchiveAutoUpdate`
   - 程序：`python E:\wx\archive\auto_update.py`（或仓库内 `project_b\auto_update.py`）
   - 触发：每日 2 次（如 08:30 与 20:30，避开大屏采集高峰）
   - 条件：仅当电脑空闲/接通电源时运行
3. **双机协同**：沿用现有模式——笔记本/台式机各配计划任务，用 `run_scheduler_weekday/weekend.py` 的模式错峰（auto_update 内置 weekday/weekend 判断开关 `--machine`）。
4. **演出确认流程**：watch_tours.py 产出 `data/pending_events.json` → 人工核对 → 确认的并入长表 xlsx → 下次构建自动带上（或直接编辑 cities.json 后跑 deploy）。
5. **repo 更新**：保留 GitHub Issues 投稿入口 + 不定期人工检索（半自动，不做爬虫）。

## 六、脚本清单（本方案交付）

| 脚本 | 职责 |
|---|---|
| `project_b/watch_releases.py` | 新歌/专辑 diff：QQ 搜索"王晰"，与 songs_meta/albums 对比，输出新增清单；`--apply` 时自动入库 |
| `project_b/watch_tavern.py` | 小酒馆新期次 diff：QQ 专辑 songlist vs tavern_audio，输出新增；`--apply` 自动入库 |
| `project_b/watch_tours.py` | 演出候选：票务搜索关键词 → `data/pending_events.json`（只读，不自动入库） |
| `project_b/auto_update.py` | 编排器：watch(可选) → 增量抓取 → deploy_all → diff 检查 → commit/push → IndexNow → 日志 |

## 七、IndexNow 通知（无感更新的最后一环）

auto_update.py 在 push 成功后调用 IndexNow（批量 POST 变化 URL，key 文件已在仓库根目录），让 Bing/搜狗/Yandex 立即重抓，实现"发布即收录"。

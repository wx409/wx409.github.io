# 知识库语义检索 · 诊断与改进方案（2026-09-07）

> 背景：用户反馈"搜索知识库提升不明显"。本文档给出根因诊断 + 可落地改进路径，
> 对应运维备忘中的下一步「全量语料按需接语义问答（kb-semantic）」。
> 现状入口：`search.html?kb=1`（旧地址 `/kb-semantic.html` 302 跳转至此）。

## 一、现在的检索是怎么工作的（读代码得出）

文件：`kb_semantic.js`（86 行，纯前端、零后端、零运行时模型）。

1. `init()` 只加载三个静态文件：
   - `data/kb/semantic/docs.json`（4699 条，含 text/type/id）
   - `data/kb/semantic/graph.json`（doc→doc 近邻）
   - `data/kb/semantic/manifest.json`（bge-small-zh, dim 512, int8, topk=8）
2. `search(query)` 打分 = **char-bigram TF 余弦 × 0.7 + 整词命中率 × 0.3**：
   - 查询与每条 doc 的文本都切成相邻两字（bigram），算余弦相似度；
   - 再按"查询的每个字是否在 doc 文本里出现"给一个词法命中分；
   - 两条合起来排序。
3. 命中 top 之后，用 graph.json 把"相关知识"延伸进来（每条最多再补几个近邻）。
4. ALIASES 别名表（低音炮/Low C/六巡/东演/青歌赛 等 14 条）在查询前做字符串展开。

## 二、为什么"语义提升不明显"（根因）

| # | 根因 | 说明 |
|---|---|---|
| 1 | **真正的向量从未参与查询** | bge 向量存在 `vectors.bin`，但只用于**离线**构建 graph.json 近邻；前端查询时 query **没有**被编码成向量（纯前端跑不动 bge）。所以"语义检索"实际是**字面 bigram 余弦**，不是语义。 |
| 2 | **中文 bigram 对短查询很碎** | "他哪年拿的青歌赛冠军" 切成两字串后，与答案文本的 bigram 重叠往往很弱；同义词、语序变化基本无效。 |
| 3 | **别名/改写面太窄** | ALIASES 仅 14 条；歌名/人物别名/年份口语化说法没有展开到 doc 文本里。 |
| 4 | **doc 文本与查询的"措辞鸿沟"** | 查询是口语问句，doc 是陈述句事实；词法检索只能靠碰字，命中率天然低。 |
| 5 | **无来源展示** | 结果只有 type 标签和 score，看不到"出自哪条数据/哪一年/哪场演出"，用户无法验证，主观觉得没用。 |

## 三、可落地改进（按性价比排序，纯静态站约束下）

### 方案 1：构建侧"查询改写 + 冗余文本"（推荐先做，零前端改动，效果最大）
在**离线构建**时（`project_b/build_kb_graph.py` 的语义索引步骤或独立脚本）为每条 doc 追加检索冗余字段，写进 `docs.json`：

- 对 fact/qa 类：把实体名（王晰/歌名/年份/城市/巡演名/机构）重复进 text 尾部，如
  `（王晰 2019 乐华娱乐 经纪人 签约 年份）`；
- 为每个 doc 预生成 3-6 条"口语化问句变体"（模板：`哪年 + 实体 + 事件`、`在哪 + 场次`、`谁 + 奖项`），用本地 ollama `nomic-embed-text` 或 qwen 离线批量改写；
- 把 ALIASES 无法穷举的别名在构建时统一落进 doc 文本。

前端无需改代码，bigram 命中率立刻上升（因为问句变体与用户查询的措辞更接近）。

### 方案 2：前端小改 kb_semantic.js（半小时级）
- 加大 ALIASES（歌名别名/常见口误/年份表达）；
- 命中 doc 前先做**类型过滤与加权**：query 含"哪年/何时"→ qa/fact 加权；含歌名 → song 加权；含城市 → city/show 加权；
- 提高词法整词命中权重、去掉 bigram 分数占比（0.7→0.5 之类），避免短查询被碎串主导；
- 结果卡片展示 `id`（含出处线索如 song:xxx / show:2026-08-23-guangzhou）与"命中原因"（命中的关键词/别名）。

### 方案 3：真向量查询（改动大，纯前端不可行，需引入本地服务）
- 若坚持"真语义"，只能把 query 编码放到构建侧不可行（查询在线）；
- 替代：把全部 doc 用 bge 编码存向量后，仍无法在无后端站点编码任意查询；
- 现实路径：GitHub Actions/本地定时任务把"预设高频问题 + 人工问题集"离线编码成 query→doc 映射表（qa_bank 扩展），用户点预设/历史问题直接命中。适合"查档"场景，不适合自由提问。

## 四、建议落地顺序
1. 先做**方案 1 + 方案 2 的 ALIASES/类型加权**（不改架构、可复算、可回退）；
2. 用 20-30 个真实问题（含"青歌赛哪年""六巡哪些城市""海政待了几年"）做 before/after 对比，把命中前 3 差异记录到本文件；
3. 评估后再决定是否投入方案 3。
